# 追踪记录（issue 与 PR 的评论）

> 一件事从提出到关闭，每一步都以固定格式的评论留在 issue 与 PR 上：人扫一眼能看懂进展，Agent 按字段就能读出状态。

## §1 生命周期

```
开 issue ──▶ 建 task 分支 + worktree ──▶ 开 PR（Closes #<issue>）──▶ 审查 + CI ──▶ 合并进 stage
   │                                                                                  │
   └──────────── 每个阶段发一条「追踪记录」评论 ─────────────┘                        ▼
                                        自动：删远端分支、关 issue、两边留言；本机：删 worktree 与本地分支
```

- **issue 是这件事的主档**：现象、复现、验收条件写在正文；之后的每一步进展写成评论，**不改写已发出的评论**（正文只补「实施」段与链接）。
- **PR 是这次改动的证据档**：解决链路、验收证据、人工验收步骤写在正文；审查与返工写成评论。
- 做完当场关：合并后必须关；不走 PR 完成的当场写「关闭」记录；只剩外部等待的关掉原 issue、剩下的开新 issue。
- 每天巡检（示例 `issue-sweep`）：关联 PR 已合并还开着的自动关闭并留记录（合并后被人重开过的、还有开着 PR 的不关）；14 天没动静的留「超期」记录；14 天内关闭却既没有合并 PR 也没有「关闭」记录的留「缺记录」，请关闭的人补上，不重开。

## §2 互相引用

| 在哪 | 写什么 | 作用 |
|---|---|---|
| 分支名 | `task/<issue>/<slug>` | 分支 → issue |
| PR 正文「关联」 | `Closes #<issue>`（只关这一个）；相关写 `Refs #n`，依赖写 `Depends on #n` | PR → issue；CI 核对与分支号一致 |
| issue 正文「实施」段 | 分支名、PR 链接、合并提交 | issue → PR |
| 评论 | 提到别的 issue/PR/提交一律写 `#n` 或完整 SHA，不写「上面那个」「刚才的 PR」 | GitHub 生成双向链接 |
| 提交信息 | 结尾 `Refs #<issue>` | 提交 → issue |

## §3 记录格式

每条评论第一行是**记录头**，之后是固定的二级字段。字段用 `**名字**：` 开头，一个字段一行或一个列表；没有内容的字段整行省略，不写「无」。

```markdown
<!-- yzgc:track v1 kind=<类型> stage=<阶段> -->
**<类型中文>**｜<一句话结论>

**现状**：<现在是什么样，一两句>
**证据**：
- <命令 + 真实输出摘要 / 截图 / 日志 / 链接>
**下一步**：<谁、做什么；已结束写「无，关闭」>
**引用**：#<issue> · #<PR> · <提交 SHA>
```

- 第一行 HTML 注释对人不可见，给 Agent 和脚本解析：`kind` 取类型表的英文值，`stage` 取 `triage | dev | review | merged | released | closed`。
- 第二行加粗中文类型 + 一句话结论 = 给人扫的标题行。
- 时间与作者由 GitHub 记录，正文不重复写。
- 证据必须是能复查的东西：命令与真实输出、截图（拖进评论框上传）、CI 运行链接、提交 SHA。「看起来没问题」不是证据。
- 不贴密钥、令牌、会话、生产数据、真实姓名；需要时写「已本地核对，不公开」。

**类型表**：

| kind | 中文 | 什么时候发 | 发在哪 |
|---|---|---|---|
| `triage` | 受理 | 确认能复现/确认要做，定了优先级和范围 | issue |
| `repro` | 复现 | 补充或更新复现步骤、设备、日志 | issue |
| `plan` | 方案 | 开工前写定位结论与打算怎么改（大改动必发） | issue |
| `progress` | 进展 | 阶段性结果：分支已建、主要改动完成、卡在哪 | issue |
| `blocked` | 阻塞 | 需要人决定、缺凭据、依赖别的 issue | issue（@ 相关人） |
| `review` | 审查 | 逐项审查结论（也可写在 PR 正文「审查结论」） | PR |
| `rework` | 返工 | 审查或验收提出的问题，以及改了什么 | PR |
| `accept` | 验收 | 人工验收结果：在哪个环境、按哪几步、看到了什么 | PR 或 issue |
| `closed` | 关闭 | 合并、发布或放弃；写明合并提交或原因 | issue 与 PR 各一条 |
| `overdue` | 超期 | 巡检自动发：开着的 issue 14 天没动静 | issue |
| `unrecorded` | 缺记录 | 巡检自动发：issue 关了却没有合并 PR，也没有「关闭」记录 | issue |

**示例**：

```markdown
<!-- yzgc:track v1 kind=plan stage=dev -->
**方案**｜开机画面进场渐变时透出了桌面，改成不渐变并等壁纸解码

**现状**：开机画面与外层同时淡入，半透明的几帧里能看到已挂好的桌面。
**证据**：
- 逐帧追踪：开机后 0.2s 内 os=0.86、boot=0.80，桌面已挂载（脚本输出）
- 慢网（壁纸延迟 2.5s）下跳过动画会露出没有壁纸的桌面
**下一步**：Claude 在 task/32/desk_boot_wallpaper 上改 Home.tsx 与 desk.css，今天提 PR
**引用**：#32
```

## §4 Agent 怎么读

- 取某 issue 的全部记录：`gh issue view <n> --json body,comments`，只看以记录头开头的评论；**最后一条的 `kind` 与 `stage` 就是当前状态**。
- 恢复上下文（新会话、压缩后）先读 issue 正文 + 最后三条追踪记录，再读关联 PR 正文与最后一条 `review`/`rework`/`accept`，**不凭记忆续做**。
- 自己做完一个阶段就发一条；不发「收到」「在做了」这类没有字段的评论。

## §5 强制点在哪

| 生命周期 | 规则 | 强制在哪 | 查不到时 |
|---|---|---|---|
| issue | 合并后 `Closes` 的必须关闭；不走的当场写「关闭」；只剩外部等待的拆新 issue | 合并时的工作流 + 合并的人当场核对；每天巡检补关 | 巡检只留记录、不重开；关不关由人决定 |
| PR | 九段正文、`Closes #<issue>` 与分支号一致、issue 开着 | PR 契约检查 | 无 |
| task 分支（远端） | 合并后立即删除 | 合并后的自动删除工作流；每周巡检残留分支只告警 | 删分支不可逆，残留由人确认后删 |
| task worktree（本机） | 合并或放弃后清理 | pre-push 检查 | 钩子需每台克隆启用一次 |
| 执行记录（`notes/`） | 开工起连续记到收尾；PR 带开工、提交、PR、审查 | 本地检查 + CI | 收尾在合并后发生，先暂存、随下一个 PR 入库 |
| 文档跟着模块改 | 模块改了对应文档同 PR 跟改；事实没变写「文档核对」 | 本地检查 + CI | 检查只看文档动没动，写得对不对靠审查 |
