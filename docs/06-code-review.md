# 代码审查（diff 审查）

> 审查是「机器可核验 + 人工判断」的第二道筛子：规定看什么、怎么判、写在哪。

## 触发时机

必须在以下任一情形发生**前**完成审查（结论写在 MR 里）：

- 任何要合入 `stage` 的 MR（含文档、脚本、配置）。
- 任何要合入 `main` 的操作（对「`stage` 当下状态」的第二道复核）。
- 部署开关打开后的镜像构建内容变更：Dockerfile、compose、`.env` 契约、部署脚本。
- 任何触及认证、授权、密钥、`.env`、数据库 schema 的改动（无论大小）。

不必逐条走完整清单的情形（纯历史材料、注释错字、私有工具目录）也要写结论：「无需逐项审查 + 理由」。

## 逐项检查清单

1. **分支不变量**：当前分支是否为 `task/<issue>/<slug>` 或 `stage`（命名符合规则）；`stage` 是否包含 `main`；是否存在把 `task/**`、`dev/**` 直接指向 `main` 的路径。
2. **是否直推 `main`**：目标分支、提交来源、CI 触发 ref；发现任何绕过 `stage` 写入 `main` 的路径即阻塞。
3. **密钥是否入库**：diff 里不得出现真实 token、密码、会话 cookie、SSH 私钥的真值。秘密扫描脚本只覆盖部分文本模式，**通过它不等于没有泄漏**，必须人眼过一遍 diff 中的新增字符串。
4. **`.env` 只允许非密值**：入库的只能是地址、端口、域名、路径、开关等可见事实；密钥字段必须留空，由 CI/CD 用环境级 secrets 注入；字段增删同步环境文档与机器配置。
5. **镜像与 compose 变更风险**：镜像 tag 语义（提交 `<sha12>`）；镜像仓库按环境分开（同一提交不得共用镜像引用，否则后构建的会覆盖前一环境）；端口不与另一环境冲突；命名卷不被改成宿主目录；健康检查仍在；Dockerfile 路径与构建上下文正确。
6. **测试与文档同步**：行为变更是否带来相应回归；改动的 API/环境变量/命令/路径是否同步到对应文档；文档索引是否重新生成。文档同步检查通过只说明文档「动过」，要对照 diff 核对改得对不对；只改「更新：」日期绕过检查的按**假同步**阻塞处理。
7. **边界规则**：模块 ↔ 文档严格对齐（新增服务必须同时补 `docs/services/<svc>/README.md`）；禁止的依赖方向（站点之间、shared → 站点、路由模块互相导入、底层反向依赖中间件、独立前端工程导入核心实现）。
8. **提交信息规范**：遵循 `<type>(<scope>): <中文简述>`；一次提交一个可独立回滚的目的；不出现 `update`/`WIP`/无信息量消息；机械搬迁与行为改变尽量分开。
9. **旧模型残留**：diff 中不得把已退役的分支模型、命名、tag 形状、部署方式当现行（历史章节必须显式标注历史）。
10. **危险操作**：数据库结构变更是否有兼容与恢复路径；是否有删除数据、覆盖配置、顺带升级无关依赖、修改生产凭据的动作；是否存在「以测试通过代替人工验收」的表述。
11. **执行记录**：本 task 的 `notes/` 链路（见 05）从「开工」起连续、已记录到「PR」；对照提交/PR/CI 核对内容属实（时间、SHA、结果对得上）；已有记录未被删除或改写。审查进行中允许暂缺「审查」记录；审查结论给出后由作者补记，届时 CI 校验补齐后方可合并。
12. **合并后清理**（合并的人在合并后当场核对）：先等这次合并触发的自动化跑完，再核对：PR `Closes` 的 issue 已关闭、远端 task 分支已删、本机 `task.mjs list --check` 通过。只有工作流失败时才当场手工关（并留「关闭」记录）；工作流还在跑时不手工关，免得留两条记录。

## 产出格式

审查结论以条目形式写进 MR 评论或 MR 描述，每条四要素：

```text
[严重度] 文件:行 — 理由（一句话，指向具体规则或真实后果）— 修法（可执行的具体动作）
```

| 严重度 | 含义 | 处理 |
|---|---|---|
| `阻塞` | 破坏不变量、泄漏密钥、越权、数据不可恢复、把历史当现行规范 | 必须修完再合并 |
| `应修` | 会带来看得见的缺陷或维护陷阱，但不阻塞本次合并 | 修，或在 MR 里写明为何本次不修 |
| `建议` | 可读性、命名、组织方式 | 作者自行决定 |

## 结论（逐字使用）

- **阻塞**：存在 `阻塞` 条目，或门禁（`pnpm verify`、必需 CI 检查）未通过。
- **有条件通过**：无 `阻塞` 条目，但有未完成的 `应修`（必须写明条件与责任人和复查方式）。
- **通过**：无未决条目，门禁通过。

不能写「基本没问题」「看起来可以」这类模糊结论；**不能用机器 PASS 代替人对 diff 的判断**。

## 记录位置

**审查记录必须写在 MR 里**（MR 描述或 MR 评论），至少包含：审查人、时间、被审查的 commit SHA、逐条结论、最终结论。不写进被审查的代码提交本身（自引用问题），也不只存在于聊天记录或本地笔记。合入 `stage` 后，MR 就是这次审查的可追溯存档。

## 与人工验收的边界

代码审查 ≠ 人工试用 ≠ 发布批准。**审查通过 ≠ 部署授权**；部署与发版是独立授权动作（见 07）。
