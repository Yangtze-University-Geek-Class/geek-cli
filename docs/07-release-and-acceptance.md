# 发布与人工验收（tag 驱动）

> 发版只靠打 tag：`vX.Y.Z-rc.N` 打在 `stage` 的提交上发预发布；验收通过后，在**同一提交**上打 `vX.Y.Z` 发正式。
> tag 不可移动、不可删除；版本号不自动提升。

## 发布模型

| tag | 形状 | 打在哪里 | 部署到 | 展示版本 |
|---|---|---|---|---|
| 预发布 | `vX.Y.Z-rc.N`（N 从 1 开始） | `stage` 上的提交（或其祖先） | 预发布环境 | `X.Y.Z-rc.N@<sha12>` |
| 正式 | `vX.Y.Z` | `main` 上的提交，且该提交上已有同一 `X.Y.Z` 的 rc tag | 正式环境 | `X.Y.Z` |

- 唯一 tag 正则（只在一处实现，测试核对多处一致）：
  `^v(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)(-rc\.([1-9]\d*))?$`
- `X.Y.Z` 必须等于**该提交里**根 `package.json` 的 `version`（不看工作区）。
- push `stage`/`main` 只跑 CI、不部署；部署只由发布 tag 触发。
- 部署开关默认关闭：开关未显式开启时，推 tag 只规划、构建镜像归档，不部署。
- 其它历史形态的 tag（`release-*`/`prev-*` 等）不触发任何部署。

## 发布流程

1. `task/<issue>/<slug>` 经审查合入 `stage`。
2. 要发的版本号还没写进 `package.json` 时，先开一个普通 task PR 改 `version`，同样合入 `stage`。
3. 所有者授权这个预发布版本后，维护者在 `stage` 的提交上打 rc tag 并推送：

   ```bash
   git fetch origin --tags && git switch stage && git pull --ff-only
   git tag -a v0.2.0-rc.1 -m "v0.2.0-rc.1" <stage 上的 40 位提交 SHA>
   git push origin v0.2.0-rc.1
   ```

4. 部署工作流核对 tag、版本号与「提交在 `stage` 上」，构建三个镜像并部署到预发布环境；部署记录 payload 带上 rc tag。
5. **所有者在预发布环境实际试用**这个 rc 的产物，按模板记录结论。不通过就在 `stage` 上修复，打下一个 `rc.N+1`，回到第 4 步。
6. 验收通过后，维护者把 `main` **快进**到被验收的提交（只允许快进；push `main` 只跑 CI）：

   ```bash
   git switch main && git merge --ff-only v0.2.0-rc.1 && git push origin main
   ```

7. 所有者授权正式发布后，在**同一提交**上打正式 tag 并推送：

   ```bash
   git tag -a v0.2.0 -m "v0.2.0" "v0.2.0-rc.1^{commit}"
   git push origin v0.2.0
   ```

8. 正式部署工作流先跑证据 job，再构建镜像，经 production 环境审批后部署。

## 授权门禁

- **打 tag 就是发版**：创建并推送任何发布 tag，都需要所有者对**这个版本号**的明确授权。「继续」「测试都过了」「CI 全绿」都不算授权；Agent 不得自行创建或推送发布 tag。
- 打正式 tag 还需要所有者在预发布环境对**同一提交**的验收记录，放行结论写明「批准发布」。
- 代码审查结论、CI 全绿、预发布部署成功、规划脚本通过，都不构成授权。
- 部署 job 按设计失败关闭时，允许的退路是用维护者机器部署同 tag 的 CI 构建产物，且同样只在上述授权之后运行；不得部署未打 tag 的提交或本机构建的镜像。

## rc 编号与版本号

- 每个 `X.Y.Z` 的 rc 从 `rc.1` 开始顺序递增，已推送的编号不复用。
- 内容有任何变化都要打新的 rc；同一 rc 要重新部署就手工重跑部署工作流（选同一个 tag），**不要为重新部署新建或移动 tag**。
- 一次只推一个发布 tag（一次推送超过三个 tag 时 GitHub 不产生 push 事件）。
- 某版本打过正式 tag 后不能再给它打 rc；下一次发版先升 `version`。
- 正式 tag 必须和其中一个 rc 落在同一提交上，且打正式 tag 时预发布站点必须仍在运行这个提交（证据 job 会读 `release.json`）。
- `version` 何时改、改成多少由所有者决定，走普通 task PR；禁止 semantic-release / 版本机器人 / 按 commit type 推算版本。

## 人工验收记录

人工验收针对**某个 rc tag 所在提交的产物**，不是对 `stage` 整条分支的一次性放行。记录至少包含：

验收人、时间（ISO 8601 含时区）、目标环境、被验收的 rc tag、完整提交 SHA（40 位小写十六进制）、被试用产物的摘要（镜像 digest 或 `/release.json`）、试用范围与结果（实际点击/操作了什么、观察到什么）、已知问题、回滚对象、明确的放行结论（批准/不批准）、可追溯的审批记录链接。

- Agent 可以整理候选改动、测试结果、差异和空白模板，**不能替验收人填写「已试用」**，不能伪造审批人或时间，不能靠 `approved=true`、环境变量或改校验器解除门禁。
- 验收记录保存在受访问控制的审批或部署记录中（GitHub Deployment、审批工单等）。
- **不要为把记录写进候选提交而制造自引用**：在候选提交之后再追加一个引用它的验收文件会产生新提交，新提交不能冒用旧验收。

## 环境隔离与展示值

- 每个环境一套完整栈：独立目录、独立编排项目、独立数据卷、独立端口、独立密钥、独立域名；不共享数据库或 Cookie 域。
- 环境变量只走每环境一份的环境文件，由部署命令消费；**非密钥项预填真实值，密钥留空**，真实值只存在于目标机，由 CI/CD 用环境级 secrets 填充。密钥不得入库、进镜像、进日志或发布记录。
- 版本展示由受控构建以 build args 注入，不从环境名猜；预发布 `X.Y.Z-rc.N@<sha12>`（`<sha12>` = 提交 SHA 前 12 位），正式只能是 `X.Y.Z`，本机明确标「本地开发 · 未发布」。
- 镜像 tag 用提交的 `<sha12>`（标识代码）；发布 tag 标识一次发版。镜像仓库按环境分开，同一提交在两个环境不共用镜像引用。

## 回滚

回滚 = 把某个环境切回一个**更早发布 tag 的镜像**；不移动分支，不移动/删除/重打 tag，不改版本号，不重置数据库：

1. 选定该环境此前部署成功过的发布 tag，算出它的镜像 tag：`git rev-parse "vX.Y.Z^{commit}" | cut -c1-12`，可在目标机部署历史里核对；
2. 在目标机运行回滚脚本，它只在**本环境**的镜像仓库里找目标镜像，把环境文件的 `IMAGE_TAG` 切到该值并重启栈；
3. 数据库结构不兼容时停下来由人处理，不用重置数据库代替回滚；目标镜像已被清理时也停下来，从该 tag 在本环境的部署产物重新分发，不在服务器上临时构建。

回滚后的修复走新的 rc（必要时先升版本号），不改写已发布的 tag。同一环境同一时刻只允许一个部署任务（串行锁）；正式环境部署不得在切换过程中被新任务取消。

## tag 不可变

- 发布 tag 一经推送就不移动、不覆盖、不删除重建。打错了就打下一个 rc 或升版本，已推送的错误 tag 保留作记录。
- 本地 pre-push 守卫拒绝删除和强制移动发布 tag；若平台侧的 tag 保护不可用，这条规则就只有本地钩子 + 工作流核对 + 流程约束，**没有服务端强制**——不要把它当成已配置的保护。

## Hotfix 与发布的关系

正式环境紧急修复按 01 的 Hotfix 规约：从 `main` 快速修上线，验收后**必须立即合回 `stage`** 恢复 `stage ≥ main`；根治靠预发布与正式环境严格同构。参见 01-git-workflow.md。
