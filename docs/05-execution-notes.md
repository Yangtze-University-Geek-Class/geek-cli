# 执行记录（`notes/`）

> 每个人、每个 agent 做的每一步，都按固定时区写进仓库里的 `notes/<日期>/<GitHub用户名>/<链路>.md`；
> 开发前先记「开工」，开发后记到「收尾」，**链路不完整的 PR 不能合并**。

## §1 为什么要有（与追踪记录的分工）

| 载体 | 记什么 | 给谁看 |
|---|---|---|
| issue / PR 评论（见 04） | 这件事走到哪一步了 | 所有人 |
| `notes/` | 谁的 agent 在什么时候做了什么、结果如何 | 出了问题时按日期和人找到每一步 |

两者都要写，不能互相代替。`notes/` 随代码一起入库，是可追溯的执行日志。

## §2 目录结构

```text
notes/
├── INDEX.md                          生成物：按日期列出每天有哪些人的记录
└── 2026-09-26/                       北京时间的日期（按固定时区，由脚本读系统时钟决定）
    └── crosery/                      负责人的 GitHub 用户名（小写）
        ├── task_91_agent_notes.md    一条链路一个文件，文件名是分支名把 / 和 - 换成 _
        └── task_87_exam_docs.md
```

- **日期**：写这条记录时的固定时区（例 `Asia/Shanghai`，+08:00）日期，不手填；一条链路跨零点时后面的记录落在新日期目录下的同名文件里，合起来仍是一条链路。
- **负责人**：替谁干活就写谁的 GitHub 用户名；agent 替某人干活，记录放在那人目录下。
- **链路**：一个 task 分支一条链路（`task/91/agent_notes` → `task_91_agent_notes.md`）；不属于任何 task 的操作（发布、验收、打 tag、排查线上问题）记在当时所在分支的链路里。
- **执行者**：每条记录单独写；同一条链路可以有多个执行者（主 agent、子代理、人）。

## §3 格式

```markdown
# task/91/agent_notes · crosery · 2026-09-26

负责人：crosery

## 00:41:07 +08:00 · 开工 · #91 · 建立 notes/ 执行记录规范

- 执行者：agent-claude-geek-main-08（Claude Code，claude-opus-5-5）
- 做了什么：从 stage f99df08 拉出 task/91/agent_notes 和独立 worktree
- 结果：worktree 在 .claude/worktrees/task-91
- 下一步：写脚本和规范正文

## 01:20:33 +08:00 · 提交 · #91 · 规范、脚本、CI 检查一起提交

- 执行者：agent-claude-geek-main-08（Claude Code，claude-opus-5-5）
- 做了什么：新增执行记录规范……；pnpm verify
- 结果：pnpm verify 通过（Tests 420 passed）
```

- 首行 `# <分支> · <负责人> · <日期>`，第二段 `负责人：<负责人>`，都与所在目录一致。
- 每条记录标题 `## HH:MM:SS +08:00 · <阶段> · #<issue> · <一句话>`；多个 issue 写 `#87 #91`，没有 issue 写 `无 issue`。
- 必填三项：`执行者`、`做了什么`、`结果`；`下一步` 可选。每项一行。
- 执行者写成 `agent-<工具>-<会话>（说明）` 或 `human-<GitHub 用户名>`。
- 「结果」写能复查的东西：命令真实输出摘要、提交 SHA、PR 号、CI 运行号、截图位置；失败就写失败，**没验证就写「未验证」**。
- **只能往文件末尾追加**，已写的记录不改不删；写错了再追加一条说明；时间只能往后走。
- 不写密钥、令牌、会话、真实个人信息和生产数据；需要时写「已本地核对，不公开」。
- 模块改了、文档事实没变时，在「做了什么」或「结果」里写 `文档核对：<文档路径> 不用改——<理由>`，文档同步检查会读它。

**阶段词表**（只允许这些）：

| 阶段 | 什么时候记 |
|---|---|
| 开工 | 开发前，链路第一条（start 脚本自动写） |
| 方案 | 定位结论和打算怎么改；大改动必记 |
| 开发 | 阶段性改动完成、重要中间结果 |
| 提交 | 每次本地提交：提交说明和跑过的检查 |
| 推送 | 推 task 分支 |
| PR | 开 PR 或改 PR 正文 |
| 审查 | 收到审查结论（谁审的、审的哪个 SHA、结论） |
| 返工 | 按审查或验收意见改了什么 |
| 合并 | PR 合进 stage，合并提交 SHA |
| 发布 | 打 rc 或正式 tag、部署运行号 |
| 验收 | 在哪个环境按哪几步看到了什么 |
| 阻塞 | 卡住了：缺授权、缺凭据、等别人 |
| 收尾 | 链路最后一条（finish 脚本自动写），之后不能再记 |

## §4 什么时候必须执行

- **开发前**：建分支和 worktree 时写下「开工」，没有开工记录不许改代码；启动时必须带身份（见 §5），缺了直接报错。
- **开发中**：每完成一个阶段就记一条，至少包括每次提交、开 PR、收到审查结论、每轮返工。
- **合并前**：PR 的链路里必须已有引用本 issue 的「开工」「提交」「PR」「审查」，并且这个 PR 新增了引用本 issue 的记录（CI 会拦）。
- **开发后**：合并、发布、验收照记；删 worktree 前写「收尾」。链路以收尾结束才算完整。
- **委派子代理时**：把身份和链路交代给它，子代理自己记，执行者写它自己。

## §5 工具与写法（示例实现）

```bash
export GEEK_NOTES_USER=crosery
export GEEK_NOTES_BY="agent-claude-geek-main-08（Claude Code，claude-opus-5-5）"

node scripts/task.mjs start 91 agent_notes     # 写「开工」
node scripts/note.mjs add --stage 提交 --issue 91 \
  --title "规范、脚本、CI 检查一起提交" \
  --did "docs(docs): …；pnpm verify" --result "pnpm verify 通过（Tests 420 passed）" \
  [--next "…"]
node scripts/task.mjs finish 91                # 写「收尾」
```

- 身份可用 `--user`/`--by` 传；两者都没有时拒绝写入。
- **记录落在哪**：当前 worktree 正在这条链路的 task 分支上时直接写进该 worktree 的 `notes/`，并重新生成 `notes/INDEX.md`，随下一次提交入库；其他情况（打 tag、在主工作区、给别的链路补记、写收尾）先暂存到主工作区（例 `.claude/notes-pending/`，已 gitignore），下一个 start 会并入新 worktree，或在任意 task worktree 里手动 flush；暂存的记录要随最近的一个 PR 入库，不能一直留在本机。
- 提交：记录和代码放同一个提交；开 PR、拿到审查结论后单独补的记录用 `docs(notes): <一句话>`。
- 合并状态以 `origin/stage` 中是否已有该 task 的链路文件判定（普通合并、squash 合并一致），不看 HEAD 的祖先关系；「合并/发布/验收/收尾」始终先暂存。

## §6 门禁

| 在哪 | 查什么 |
|---|---|
| 本地 `pnpm check` | 目录只能是 `<日期>/<用户名>/<链路>.md`；标题、负责人和目录一致；每条记录的标题、阶段和必填项；时间不倒退；每条链路第一条是「开工」、收尾之后没有记录；`INDEX.md` 是最新的 |
| CI（task 分支进 stage 的 PR） | 上面全部 + 本 task 的链路存在；有引用本 issue 的「开工」「提交」「PR」「审查」；本次 PR 新增了引用本 issue 的记录；已有记录未被改写或删除（**严格只追加**） |

检查不过就补记录；**不许改检查脚本来换绿色，也不许补写没发生过的事**。脚本只核对格式与「记没记」，内容是否属实由审查人对照提交、PR、CI 核对。
