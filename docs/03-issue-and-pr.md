# Issue 与 PR

## 一、Issue：一件事的主档

### 开发前先开 issue

- **任何 `task/<issue>/<slug>` 分支都必须先有对应 issue**；唯一例外是明确声明的紧急修复，且事后 24 小时内补 issue。
- **先查重再开新**：按模块、关键词、错误信息搜索（含已关闭）；重复的直接在原 issue 补一条「复现」记录，不另开。
- **一件事一个 issue**：一次提了几件事时，能一起验收的放一个 issue，不能一起验收的拆开、互相 `Refs #n`。

### 正文内容

**缺陷**（标题 `<模块>：<用户可见的症状>`）：

| 段落 | 要求 |
|---|---|
| 现象 | 实际看到了什么：报错原文、截图（拖进编辑框上传）、录屏；动画问题附逐帧图 |
| 复现步骤 | 最小路径，编号，每步写操作与看到的结果；偶发的写复现概率与已知条件 |
| 期望 | 应该是什么样 |
| 影响 | 谁会遇到、多严重、有没有绕过办法（决定优先级） |
| 环境 | 见下方「环境与设备」 |
| 验收条件 | 怎样算修好：可观察结果 + 要在哪些尺寸/设备/环境看 |

**需求 / 改进**（标题 `<模块>：<用户可见的诉求>`）：现状与问题（**不要写实现方案**，方案放 PR 的「解决链路」）、期望结果、范围与**不做什么**、接口/权限/数据影响、验收条件、已考虑过的替代方案。

**优先级**：P0 = 阻断核心流程 / 数据或权限风险 / 线上不可用；P1 = 主要功能受损但可绕过，或已明确排期；P2 = 其余。不确定宁可低一档，**禁止虚高 P0**。未经复现的怀疑标为「待确认」，不用肯定语气写「已证实」。

### 环境与设备

**必填**：

- 分支与完整 commit SHA（写现行分支名，不写已退役的名字）；
- 站点与地址（本机 / 预发布 / 正式各写各的）；
- 页面显示的版本（正式 `X.Y.Z`，预发布 `X.Y.Z-rc.N@<sha12>`，能对应到发布 tag 时一并写）。

**按问题类型补充**（无关的不写，不为凑字段填）：布局 → 视口尺寸、设备像素比、横竖屏；动画/帧率 → 浏览器与版本、GPU/机型、刷新率、是否前台真实浏览器（自动化浏览器会把动画页限在约 30Hz，不能用来判断帧率）；触屏 → 设备型号、系统版本、浏览器；登录/权限 → 身份（游客/成员/哪个称号）；接口/数据 → 请求路径、状态码、`requestId`。

**安全**：不贴会话、令牌、cookie、完整请求头或真实数据；安全问题私下报告。

### 关闭规则

- 关闭前 issue 上必须能查到对应 PR 与验证结果；不能仅因「代码存在」或「构建成功」就关闭功能缺陷。
- **PR 合并进 `stage` 后，它 `Closes` 的 issue 必须关闭**，分支与 worktree 必须清理（GitHub 自带的 `Closes #n` 只在合进默认分支时生效，不能依赖）。
- 不走 PR 做完的（运维操作、决定不做、重复、被别的改动顺带解决）：做完的人**当场**写「关闭」记录（做了什么、在哪验证、或为什么不做、被哪个 `#n` 取代）再关闭，不静默关闭。
- 只剩外部等待的：关掉原 issue，把剩下的那一步开成新 issue，写明负责人和在等什么，两边 `Refs` 互相引用。
- 一件事做不完：在原 issue 留「阻塞」或「拆分」记录，拆出的新 issue 互相 `Refs`；不在已合并的分支上继续提交。

## 二、PR：一次改动的证据档

### 目标与生命周期

- PR 只能指向 `stage`；`main` 不接受来自 `task/**`、`dev/**` 的 PR。
- 一件事 = 一个 issue = 一个 task 分支 = 一个 PR；**PR 正文标题遵循提交信息规范**。
- 合并进 `stage` 后：issue 关闭、远端分支删除、worktree 清理；已合并的 PR 不再追加提交，验收发现的新问题开新 issue 并 `Refs #<原 issue>`。

### 正文契约：九个段落一个都不能少

CI 逐项核对（改 PR 描述会自动重跑）：

| 段落 | 要求 |
|---|---|
| 目的 | 解决什么问题、谁提的、为什么现在做；引用 issue 里的原话 |
| 关联 | `Closes #<issue>`（只关这一个，与分支号一致）；相关写 `Refs #n`，依赖写 `Depends on #n` |
| 变更范围 | 按服务列出改了什么，再写明「不做什么」 |
| 解决链路 | 复现 → 定位（根因与怎么确认的）→ 修复（为什么这样改、否决了什么）→ 验证（能区分修复前后的回归） |
| 验证命令与结果 | 实际跑过的命令 + 真实输出摘要；失败、跳过、未验证的逐条列出 |
| 验收证据 | 界面改动放改前/改后截图（桌面与手机各一），动画放逐帧拼图或录屏；每项写编号、尺寸/设备、对应验收点；没有界面变化写「无界面变化：<理由>」 |
| 人工验收步骤 | 给验收人照着做的清单：打开哪个地址（写版本或 commit）→ 做什么 → **应看到**什么 |
| 审查结论 | 按审查清单逐项；审查人、时间、被审查 commit；最后一行 `**结论：通过**` / `**结论：有条件通过**` / `**结论：阻塞**` |
| 风险与回滚 | 已知风险、没覆盖到的环境、回滚方式（revert 合并提交 / 切回更早的镜像 tag） |

- 截图与录屏直接拖进 GitHub 编辑框上传；**本机路径（`/tmp/...`）别人看不到，不算证据**。
- 修复漏洞时不要把真实凭据或可利用的生产数据放进公开讨论。

### 评论

- 审查意见、返工、验收结果写成评论，统一用追踪记录格式（见 04）的 `review`/`rework`/`accept`；**不改写已发出的评论**。
- 审查进行中允许暂缺「审查」的执行记录；审查结论给出后由作者补记再合并。

### 门禁

- 根验收入口（如 `pnpm verify`）必须通过；相关浏览器用例通过或明确标为待验收。
- task 分支的 PR 要有完整执行记录：链路里有引用本 issue 的「开工」「提交」「PR」「审查」，且本次 PR 新增了记录。
- 文档索引与相对链接有效；无密钥、真实业务数据库、依赖缓存或无关改动。
- **不得通过删除失败断言、复制 handler、伪造返回值或跳过检查来取得绿色**。
- CI 文件是否被远端执行、分支保护是否生效，需仓库管理员实际配置确认；本地有命令 ≠ 远端有保护。
